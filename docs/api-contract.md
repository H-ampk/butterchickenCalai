# API連携方針

フロントエンドとバックエンドの連携方針です。この文書は実装済みの契約ではありません。

この改訂は [Issue #42](https://github.com/H-ampk/butterchickenCalai/issues/42) に、開発責任者との設計検討で採用した読み取り方針を記録します。学科長・企業側の承認や、チーム全体の正式レビューが完了したという意味ではありません。Workers API、D1 の migration、フロントエンドの実装は、この改訂では変えていません。

[Issue #4](https://github.com/H-ampk/butterchickenCalai/issues/4) は、この仕様作業の再編成前の Issue です。仕様の合意が終わったという意味では扱いません。読み取りの実装は [Issue #45](https://github.com/H-ampk/butterchickenCalai/issues/45) の範囲です。#45 は、下の「開発責任者との設計検討で採用した方針」を読み取りの前提にします。学科長・企業側の未決定事項を、#45 の実装の中で埋めません。

## 現行の実装

### 店舗の型

現行の店舗型は [frontend/src/types/shop.ts](../frontend/src/types/shop.ts) です。次の 5 項目はすべて必須です。

```typescript
export interface Shop {
  id: string
  name: string
  address: string
  latitude: number
  longitude: number
}
```

| 項目 | 現行の型 | 用途 |
| --- | --- | --- |
| `id` | `string` | 店舗の識別子。モックでは `dev-shop-01` のような文字列 |
| `name` | `string` | 店舗名。検索の対象 |
| `address` | `string` | 住所。検索の対象 |
| `latitude` | `number` | 緯度。地図と座標の有効判定 |
| `longitude` | `number` | 経度。地図と座標の有効判定 |

### 割引の暫定型

[frontend/src/types/discount.ts](../frontend/src/types/discount.ts) に、前回草案へ合わせた暫定の `Discount` があります。コード上の合意済みの型ではありません。`subject` と `content` という名前、`startsAt` が `null` のときの意味は、型コメントでは未合意のままです。画面の一覧はこの型を表示していません。設計検討での意味は後の節にあり、この改訂では型コメントを変えていません。

### モックと取得

[frontend/src/api/mockShops.ts](../frontend/src/api/mockShops.ts) は、広島市内に散らした架空の店舗を 5 件持っています。店名、住所、位置は実在の割引情報ではありません。各要素は上の 5 項目だけです。

[frontend/src/api/mockDiscounts.ts](../frontend/src/api/mockDiscounts.ts) は、架空の割引を持っています。販売終了後の行も残しています。

[frontend/src/api/shops.ts](../frontend/src/api/shops.ts) の `getShops()` の戻り値の型は `Promise<Shop[]>` です。画面は `getShops()` だけを使い、モック配列を直接参照しません。既定はモックで、API へ通信しません。`VITE_DATA_SOURCE=api` のときだけ、Workers の仮パスへ通信します。通信に失敗してもモックへは戻しません。

前回のこの節は、`getShops()` が API へ通信しないと書いていました。[#81](https://github.com/H-ampk/butterchickenCalai/pull/81) のあと、既定のモックに加えて API モードがあります。この改訂でその記述を、実装に合わせています。

地図画面 [frontend/src/pages/MapPage.tsx](../frontend/src/pages/MapPage.tsx) は、`name`、`address`、`latitude`、`longitude` を表示します。

### 仮の一覧取得

[frontend/src/api/workersApi.ts](../frontend/src/api/workersApi.ts) のパスは、コード上の仮の値です。設計検討で採用したパスとは別です。この改訂では定数を変えていません。

| 定数 | 現行の仮パス |
| --- | --- |
| `PROVISIONAL_SHOP_LIST_PATH` | `GET /shops` |
| `PROVISIONAL_DISCOUNT_LIST_PATH` | `GET /discounts` |

仮のクライアントは、一覧の JSON が `items` 配列を持つオブジェクトであることを要求します。配列そのものを返す応答は形式不一致にします。`limit` と `offset` は付けません。コードのコメントは、既定値が未合意であると書いています。`total` は読みません。設計検討では既定値を採用していますが、この改訂ではクライアントを変えていません。

店舗の要素は、`id`、`name`、`address` が文字列であり、`latitude` と `longitude` が有限な数であることを要求します。`createdAt` と `updatedAt` は要求しません。割引の要素は、暫定の `Discount` の各項目を要求します。`startsAt` と `endsAt` の項目が無い応答を `null` には置き換えません。省略と明示的な `null` を同じに扱うかは、書き込み入力の未決定のままです。

### 検索が参照する項目

[frontend/src/utils/shopSearch.ts](../frontend/src/utils/shopSearch.ts) の参照範囲は次のとおりです。

- `searchShops` は `name` と `address` だけを見ます。比較の前に NFKC 正規化、前後の空白除去、`toLowerCase` を行います。空になった検索語は、検索条件なしとして全件を返します。店舗名または住所のどちらかに部分一致すれば該当です。
- `filterShops` は、検索に加えて `hasCoordinates` を選べます。有効な座標は、有限数であり、緯度が -90 以上 90 以下、経度が -180 以上 180 以下です。境界値は有効です。`NaN` と `Infinity` は無効です。
- 割引の項目は見ていません。

現行の検索実装はクライアント側です。サーバー側の `q` は設計検討で採用しました。この改訂では、そのクエリをコードへ足していません。

### 販売期間の既存判定

[frontend/src/api/discountPeriod.ts](../frontend/src/api/discountPeriod.ts) の `classifyDiscountForNormalList` は、通常一覧へ含めるかを判定します。画面からは呼ばれていません。決定済みとして扱っているのは、開始より前の除外、終了日時を過ぎたあとの除外、開始時刻ちょうどは開始前ではない、という範囲です。次は未決定として、含めも除外もしていません。

- `endsAt` と現在時刻が同時
- `startsAt` が `null`
- タイムゾーンの無い日時、実在しない暦日、解釈できない現在時刻

`endsAt` が `null` で `startsAt` に時刻がある場合は、終了による除外をしません。`startsAt` が `null` の場合は、終了による除外に該当しなければ `undecided` を返します。この関数は、この改訂では変更していません。設計検討との差は「既存の期間判定との差」に書きます。

### 割引の試作

[frontend/src/api/main.py](../frontend/src/api/main.py) は、FastAPI の試作です。割引の配列をプロセスのメモリに持っています。D1 にも PostgreSQL にも接続せず、認証もありません。フロントエンドの `main.tsx` からは呼ばれていません。採用予定の Workers API ではありません。

試作が持つ項目は、数値の `id`、`shop_name`、`content`、`tags`、`latitude`、`longitude` です。`GET /discounts` と `POST /discounts` があります。このパスと項目は、設計検討で採用した読み取りではありません。

この改訂では TypeScript を変えません。実装時に必須項目を増やす、名前を変える、型を変える場合は、少なくとも次を見直します。

- `frontend/src/api/shops.ts`
- `frontend/src/api/discounts.ts`
- `frontend/src/api/workersApi.ts`

レスポンスへ項目を足すだけなら、現行の画面は知っている 5 項目だけを読めます。`getShops()` の戻り値を配列以外にする場合は、この関数の利用者を合わせます。仮のクライアントは、通信の応答では `items` を読み、関数の戻り値では配列に戻しています。

## 既に合意された方針

次は、この設計検討より前に方針として採用しているものです。設計検討の節と、決定に含めなかった候補は、ここに含めません。

- データ交換形式は JSON。通信の方式としては HTTP を使う。公開時の通信は HTTPS。詳細は [architecture.md](architecture.md)
- API 設計には OpenAPI を使う。OpenAPI の定義ファイルは、この改訂ではリポジトリに追加しない。追加する時期は未決定
- 採用した仕様で、TypeScript の型、Cloudflare Workers の API、Cloudflare D1 の列を揃える。FastAPI の試作はその仕様ではない
- 共有する店舗と割引は、Workers の API を経由して D1 に保存する。ブラウザから D1 を直接更新しない。ローカルの Wrangler と `GET /__health` は [workers-local.md](workers-local.md) にある。これは店舗・割引 API ではなく、この文書の決定でもない。リモート D1、店舗・割引のエンドポイント、デプロイは未作成。構成の詳細は [architecture.md](architecture.md)
- D1 は SQLite 系である。PostgreSQL の専用の型や関数は使わない
- 登録、更新、削除の認証と認可は [Issue #58](https://github.com/H-ampk/butterchickenCalai/issues/58) に残す。公開 GET の認証要否は、下の設計検討で採用した
- インデックス、残っているチェック制約、migration ファイルの作成は [Issue #63](https://github.com/H-ampk/butterchickenCalai/issues/63) が行う。[database/README.md](../database/README.md) はこの改訂では変えていない
- `endsAt` が `null` の割引は期限なしとする。販売終了後の割引は通常の一覧から外し、D1 の行は削除しない。比較の実装は [Issue #50](https://github.com/H-ampk/butterchickenCalai/issues/50)
- 店舗を物理削除する場合に限り、その店舗を参照する割引も外部キーの `ON DELETE CASCADE` で削除する。D1 で外部キーを有効にする手順は #63 が書く。店舗を削除できる人は #58
- 読み取り API の実装 Issue #45 では、登録、更新、削除を作らない
- API を変更するときは、フロントエンド、バックエンド、データベース、全体管理の関係担当者に共有する

文字コードは UTF-8 を、前回草案から引き続き候補に残します。この節には上げていません。

### 読み取り API

店舗と割引の公開読み取りは、次の 5 本です。`/api/v1` は版を分ける接頭辞です。`GET /__health` はこの 5 本に含まれません。

| メソッド | パス | 用途 |
| --- | --- | --- |
| GET | `/api/v1/shops` | 店舗一覧。`q` を受け付ける |
| GET | `/api/v1/shops/{shopId}` | 店舗詳細 |
| GET | `/api/v1/discounts` | 割引一覧 |
| GET | `/api/v1/discounts/{discountId}` | 割引詳細 |
| GET | `/api/v1/shops/{shopId}/discounts` | 店舗別割引一覧 |

現行コードの仮パス `GET /shops` と `GET /discounts`、試作の `GET /discounts` と `POST /discounts` は、この 5 本ではありません。コード上の定数は、この改訂では変えません。

POST、PATCH、PUT、DELETE のパスは決めません。登録、更新、削除の成功ステータスも決めません。書き込みの認証と認可は #58 です。

JSON の項目名は camelCase です。D1 の列名は snake_case です。Workers が公開 JSON と列名を変換します。

一覧の成功応答は次の形です。詳細の成功応答は、リソースそのものです。`shop` や `discount` では包みません。

```json
{
  "items": [],
  "total": 0,
  "limit": 20,
  "offset": 0
}
```

| 規則 | 採用した内容 |
| --- | --- |
| ページング | offset 方式 |
| `limit` の既定値 | 20 |
| `limit` の上限 | 100 |
| `offset` の既定値 | 0 |
| 一覧が 0 件 | HTTP 200。空の `items`。404 にはしない |
| `offset` が該当件数以上 | HTTP 200。空の `items` |
| 詳細の行が無い、または公開対象外 | HTTP 404 `not_found` |
| 並び順 | `created_at DESC, id ASC` |
| `total` | 公開条件と検索条件を適用したあと、ページ分割の前の件数 |
| 応答の `limit` と `offset` | 適用した値を返す |
| 公開 GET の認証 | 不要。対象は上の 5 本 |

並び順が保証するのは、同一のデータ集合を同じ条件で読んだときの順序です。`id ASC` は、`created_at` が同じ行の相対順を決めます。`offset` は、リクエストのたびにその時点の集合を先頭から数えます。次のページまでに行が増えると、既に返した行が再び出ることがあります。行が減ると、まだ返していない行を飛ばすことがあります。この重複と取りこぼしは、初期実装では保証対象外です。カーソル方式とスナップショット方式は使いません。

`limit` が 1 以上 100 以下の整数でない、または `offset` が 0 以上の整数でない場合は、HTTP 400 `invalid_request` です。

`limit` または `offset` が複数ある場合も、HTTP 400 `invalid_request` です。値が同じでも拒否します。最初の値も最後の値も採用しません。重複した値のどちらを採るかが曖昧になるためです。同じ値だけを例外にすると、実装ごとの解釈が分かれます。店舗一覧の `q` の重複指定も HTTP 400 `invalid_request` であり、一覧の `limit` と `offset` も同じ扱いにします。この規則は、今回の開発上の設計検討で採用した方針です。学科長・企業側の承認や、チーム全体の正式レビューの完了ではありません。

エラー応答は次の形に統一します。`message` は利用者が読める文です。内部例外、SQL、接続情報、秘密情報は返しません。

```json
{
  "error": {
    "code": "not_found",
    "message": "対象のリソースが見つかりません。"
  }
}
```

| HTTP | code | 内容 |
| --- | --- | --- |
| 400 | `invalid_request` | 不正なリクエスト |
| 404 | `not_found` | 行が無い、または公開対象外。クライアントは、存在と非公開を応答だけでは区別できない |
| 405 | `method_not_allowed` | 許可されていない HTTP メソッド |
| 500 | `internal_error` | バインディング不足、SQL の不具合、予期しない例外 |
| 503 | `service_unavailable` | DB に接続できない一時障害 |

401 と 403 は、この 5 本の公開 GET では使いません。書き込みで使う条件は #58 です。項目ごとの `details`、`validation_error`、409、422 は、この読み取りには含めません。

### 公開条件

公開対象の絞り込みは、ページングより前に行います。`total` はその件数です。公開対象から外した行は削除しません。

店舗を公開するには、有効な緯度と経度の両方が必要です。有効な座標は、現行の `filterShops` と同じです。有限数であり、緯度が -90 以上 90 以下、経度が -180 以上 180 以下です。境界値は有効です。座標が欠けている、片方だけがある、範囲外、または数として不正な店舗は、一覧にも詳細にも出しません。詳細は HTTP 404 です。

割引を公開するには、次をすべて満たします。

- `subject` と `content` の少なくとも一方が、trim 後に空でない
- 保存されている日時が正当である。正当な形式は「日時」の節の `YYYY-MM-DDTHH:mm:ssZ` であり、暦として存在する
- `startsAt` と `endsAt` の両方が存在するとき、開始が終了より前である
- 紐づく店舗が、上の条件で公開可能である

`subject` と `content` は、この公開条件で使う項目名です。別名にはしません。両方に値があってもよいです。片方だけが空でも、もう一方が trim 後に空でなければ公開条件のこの項は満たします。両方とも空、または空白だけの行は公開しません。これは商品名を必須列にする決定ではありません。商品名、定価、割引価格、在庫数の列は追加しません。

通常の割引一覧と店舗別割引一覧には、上の公開条件を満たし、かつ販売期間中の割引だけを含めます。販売期間は「日時」の節です。

割引詳細は次のとおりです。

| 状態 | 詳細 |
| --- | --- |
| 開始前 | 404 |
| 販売中 | 200 |
| 終了済みで、他の公開条件を満たす | 200 |
| 不正な保存データ | 404 |
| 非公開の店舗に属する | 404 |
| 行が無い | 404 |

開始前は販売期間中ではないため、一覧にも含めません。終了済みも一覧には含めません。終了済みであることを理由に行は消しません。`status` 列は追加しません。

公開できない店舗に対する `GET /api/v1/shops/{shopId}/discounts` は、空の一覧にはしません。店舗詳細と同じく HTTP 404 です。公開できる店舗に販売期間中の割引が無いときは、HTTP 200 と空の `items` です。

承認の要否は、学科長・企業側の確認事項のままです。管理者承認用の列は、今回のスキーマには追加しません。座標と上の割引条件以外の業務上の公開ゲートは、その確認が終わるまで追加しません。

### 検索

初期の店舗検索では、`GET /api/v1/shops` に `q` を含めます。対象は店舗名と住所です。割引一覧の検索クエリにはしません。割引の各 GET に `q` が付いている場合は、未知のクエリパラメータとして HTTP 400 です。

- 比較の前に、NFKC 正規化、trim、小文字化を行う。現行の `normalizeSearchText` と同じ変換です
- 正規化後の店舗名、または正規化後の住所に、正規化後の `q` が部分一致すれば該当とする
- D1 には `name_search` と `address_search` を保存する。公開 JSON には出さない
- 登録と更新では、元の `name`、`address` と、二つの検索列を、同じ DB 操作で保存する
- 正規化関数を変えたときは、検索列をその関数で再構築する
- 絞り込みはページングより前に行う。`total` は、公開条件と `q` を適用したあと、ページ分割の前の件数である

SQLite の `LIKE` では、利用者の `q` に含まれる `%`、`_`、およびエスケープ文字自体をエスケープします。部分一致のための `%` は、エスケープしたあとで前後に付けます。`ESCAPE` 句を付けます。SQL の値はパラメータバインディングで渡し、利用者入力を SQL 文へ連結しません。

`q` の上限は、正規化後 200 文字です。超えた場合は HTTP 400 `invalid_request` です。正規化後に空になる、空白だけの `q` は、検索条件なしとして扱います。`q` の重複、未知のクエリパラメータ、不正な URL エンコードは HTTP 400 `invalid_request` です。一覧の `limit` と `offset` の重複指定も、値が同一でも同じ `invalid_request` です。パーセントエンコードの形式が正しくても、UTF-8 として復号できないクエリは不正な URL エンコードとして同じ `invalid_request` です。

`includeEnded` は初期のクエリに含めません。終了済みを一覧へ戻す指定は、将来の拡張です。割引一覧の `shopId` クエリも使わず、店舗の指定は `GET /api/v1/shops/{shopId}/discounts` で行います。

### 日時

D1 の日時は、UTC の ISO 8601 を `TEXT` で保存します。形式は `YYYY-MM-DDTHH:mm:ssZ` です。成功応答の日時もこの形式です。Unix 秒の `INTEGER` は使いません。小数秒付きの入力は拒否し、HTTP 400 `invalid_request` にします。

保存値がこの形式でない、または暦として存在しない場合は、不正な保存データです。公開対象から外し、詳細は HTTP 404 です。行は削除しません。

| 条件 | 意味 |
| --- | --- |
| `startsAt` と同時刻 | 販売開始。終了より前なら通常一覧に含める |
| `endsAt` と同時刻 | 販売終了。通常一覧から外す。他の公開条件を満たせば詳細は 200 |
| `startsAt: null` | 開始制限なし |
| `endsAt: null` | 終了制限なし。これは既に合意された方針 |
| 両方 `null` | 期間制限なし。他の公開条件を満たせば販売期間中 |
| 両方に値があり、開始が終了以降 | 不正な保存データ。公開しない。詳細は 404。行は削除しない |

比較は UTC で行います。販売期間中とは、適用される境界について `startsAt <= now < endsAt` であることです。`null` の境界は適用しません。

日本標準時は UTC+9 で、夏時間はありません。保存形式にはしません。表示に使うかは、この節では決めていません。

SQLite の `datetime('now')` は `YYYY-MM-DD HH:MM:SS` であり、`T` と `Z` がありません。この形式と、保存している ISO 8601 を混ぜて大小比較しません。

書き込み入力で、オフセット付きの日時を受理して UTC へ正規化するかは未決定です。オフセットの無い日時と、日付だけを書き込みで受けるかも未決定です。保存と成功応答の形式は、上の `Z` で秒までです。

### 既存の期間判定との差

`classifyDiscountForNormalList` は、この改訂では変更していません。設計検討との差は次のとおりです。

| 入力 | 現行の関数 | 設計検討で採用した扱い |
| --- | --- | --- |
| `startsAt` ちょうどで、終了より前 | `include` | 販売開始。一覧に含める。詳細は 200。一致 |
| `startsAt` より前 | `exclude` / `not-started` | 一覧から外す。詳細は 404。一覧の除外は一致し、詳細の 404 は現行関数の範囲外 |
| `endsAt` より後 | `exclude` / `ended` | 一覧から外す。他の公開条件を満たせば詳細は 200。一覧の除外は一致 |
| `endsAt` ちょうど | `undecided` / `ends-at-boundary` | 販売終了。一覧から外す。他の公開条件を満たせば詳細は 200。不一致 |
| `startsAt` が `null` で、終了条件には掛かっていない | `undecided` / `starts-at-null` | 開始制限なし。終了条件だけを見る。両方 `null` なら期間制限なし。不一致 |
| `endsAt` が `null` で、`startsAt` は時刻があり開始済み | 終了では除外しない | 終了制限なし。一致 |
| 形式が不正、または暦として無い日時 | `undecided` / `invalid-datetime` | 公開しない。詳細は 404。行は削除しない |

この関数の `undecided` を、コード上で除外や採用へ置き換える作業は、この文書の改訂には含めません。通常一覧から外す実装の主体は #50 です。#45 は、この節の規則で一覧と詳細を読みます。

### D1 とエラー

テーブルは `shops` と `discounts` の 2 つです。主キーは `TEXT` です。API の `id` と同じ文字列を使います。API に SQLite の `rowid` は出しません。

割引の `shop_id` は `shops.id` を参照する外部キーです。店舗を物理削除するときは `ON DELETE CASCADE` を使います。この連鎖削除は、既に合意された方針です。D1 で外部キーを有効にする手順は #63 が書きます。

日時列は、上の形式の `TEXT` です。終了フラグ列は作りません。商品名、定価、割引価格、在庫数、管理者承認の列は追加しません。

検索列は `shops.name_search` と `shops.address_search` です。

migration は Wrangler migrations を使います。ローカル専用の seed は、migration と分けます。この改訂では migration ファイルも seed も作りません。現行の [workers/wrangler.jsonc](../workers/wrangler.jsonc) は変えません。ローカルのバインディング名は `DB` です。これは [workers-local.md](workers-local.md) のローカル設定であり、本番の `database_id` はありません。本番公開はしません。

識別子の生成方法は未決定です。空でない `TEXT` であることは、この節で採用しています。UUID にするかは決めていません。PostgreSQL の UUID 型は使いません。

DB に接続できない一時障害は HTTP 503 `service_unavailable` です。バインディング不足、SQL の不具合、予期しない例外は HTTP 500 `internal_error` です。どちらの本文にも、内部エラーと SQL の詳細は入れません。

### フロントエンドの実装方針

次はフロントエンド側の実装方針です。API の応答契約ではありません。この改訂ではフロントエンドのコードを変えていません。現行の取得口は、上の「現行の実装」のままです。

- offset 方式による取りこぼしと重複は、初期実装では保証対象外とする

## 接続先

フロントエンドが API の基底 URL を参照する環境変数は `VITE_API_BASE_URL` です。値の例は [frontend/.env.example](../frontend/.env.example) にあります。実際の `.env` は Git の管理対象外です。

例の値は `http://localhost:8000` のままです。旧設計のローカル待受を想定しています。設計検討で採用したフロントエンド方針は、同一オリジンの相対パスです。これは API の応答契約ではありません。この改訂では、環境変数の例もコードも変えていません。
