# 共同開発ガイド

5人のチームで地域割引SNSアプリを開発するための手順です。

## Issue

機能追加や修正は、Issue を作成してから着手します。GitHub の New issue からテンプレートを選び、項目を埋めて作成します。調査や、テンプレートに当てはまらない作業は、空白の Issue を使います。

### テンプレートの使い分け

| テンプレート | 使うとき |
| --- | --- |
| [機能追加・改善](../.github/ISSUE_TEMPLATE/feature_request.md) | 新機能の実装や、既存機能の改善 |
| [バグ報告](../.github/ISSUE_TEMPLATE/bug_report.md) | 再現できる不具合 |
| 空白の Issue | 調査、相談、上記に当てはまらない作業 |

機能追加・改善では、目的、機能概要、対象領域、作業内容、完了条件、依存関係を書きます。バグ報告では、概要、再現手順、期待する動作と実際の動作、発生環境、対象領域、修正の完了条件を書きます。

## Pull Request

変更は Pull Request で統合します。作成画面には [Pull Request テンプレート](../.github/pull_request_template.md) が入ります。関連 Issue、変更概要、変更内容、動作確認、テスト結果、UI 変更、注意事項、レビューチェックリストを埋めてからレビューを依頼します。

Issue との関連付けは次のとおりです。

- マージ時に Issue を閉じる場合は `Closes #番号`
- Issue を閉じない場合は `Refs #番号`

原則として、担当者以外がレビューします。レビューでは次を確認します。

- 関連 Issue が記載されている
- 変更内容が説明されている
- 必要なテストを実施している
- Frontend CI が成功している。対象外の場合は、その理由が書いてある
- 秘密情報や、無関係な変更が含まれていない

画面変更がない Pull Request に、スクリーンショットや E2E テストは不要です。マージ前に、その変更で必要なテストを実行します。

## 継続的インテグレーション

`main` 向けの Pull Request を作成または更新すると、Frontend CI（`.github/workflows/frontend-ci.yml`）が実行されます。`main` への push と、GitHub Actions 画面からの手動実行でも同じワークフローが動きます。

Frontend CI は、フロントエンドの TypeScript 型チェックと Vite の本番ビルドを行います。依存関係は `frontend/package-lock.json` を使った `npm ci` でインストールします。

レビューとマージの前に、CI が成功していることを確認してください。失敗した場合は、ログで原因を特定し、同じ作業ブランチで修正して push します。push すると CI が再実行されます。失敗したままマージしません。

CI の成功は、型チェックとビルドが通ったことだけを示します。アプリの全機能が動作することの保証ではありません。バックエンド、データベース、自動テストは、このワークフローの対象外です。

## コード管理

- 作業単位は可能な限り小さくする
- 無関係な変更を同じ Pull Request に含めない
- 他メンバーの担当領域を無断で大幅に変更しない
- APIやデータベース構造を変えるときは、関係担当者と調整する
- 依存パッケージを追加するときは、理由を説明する

## ブランチ

`main` は動作確認済みのコードを保持します。原則として `main` へ直接 push しません。作業ブランチは Issue ごとに作ります。

例:

```text
feat/home-page
feat/shop-registration
feat/post-api
feat/map-view
fix/login-error
docs/update-readme
```

## セキュリティ

- `.env` や秘密情報を GitHub に登録しない
- パスワードを平文で保存しない
- 店舗の投稿を編集・削除する処理には、所有権の確認を必要とする
- フロントエンドの表示制御だけで権限制御を完結させない
